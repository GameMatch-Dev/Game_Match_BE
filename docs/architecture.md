## 왜 헥사고날 아키텍처를 선택했나

경기 생성과 참가 승인에는 모집 상태, 남은 정원, 신청 상태처럼 함께 판단해야 하는 규칙이 있습니다. 경기 생성 기능을 만들면서 규칙을 처리하는 코드에 JPA 엔티티 변환과 저장 과정까지 섞이면, 어느 코드가 경기 규칙을 결정하는지 따라가기 어려웠습니다.

계층형 구조에서도 서비스를 잘 나누면 이 문제를 해결할 수 있습니다. GameMatch에서는 유스케이스가 저장에 필요한 동작을 포트로 정의하고 JPA 어댑터가 그 계약을 구현하도록 경계를 명시했습니다. 이렇게 하면 유스케이스를 읽을 때 경기 규칙과 처리 순서에 집중할 수 있고, 조회 쿼리나 엔티티 매핑을 변경할 때 수정 범위를 영속성 어댑터 쪽으로 좁힐 수 있습니다. 경기 규칙을 DB 없이 검증할 때도 포트에 테스트 구현을 넣을 수 있습니다.

그 대신 포트, 어댑터, 변환 코드가 늘어 단순한 조회까지 여러 파일을 거쳐야 할 수 있습니다. 이 구조의 이점은 경기나 신청처럼 규칙이 있는 기능에서 가장 크며, 조회 최적화는 영속성 어댑터에 두는 것이 설계 기준입니다.

## 요청 처리 흐름

> HTTP 요청 → 입력 어댑터 → 유스케이스 → 출력 포트 → JPA 어댑터 → DB

웹 요청과 DB 접근을 어댑터로 나누고, 유스케이스가 필요한 저장 동작을 포트로 정의합니다. 예를 들어 게임 프로필 검색에서는 컨트롤러가 검색 조건을 받아 유스케이스에 전달하고, 영속성 어댑터가 프로필과 연결 데이터를 조회해 반환합니다.

| 계층 | 책임 |
| --- | --- |
| 입력 어댑터 | HTTP 요청을 받아 유스케이스를 호출하고 결과를 응답으로 변환 |
| 애플리케이션 | 요청의 처리 순서와 필요한 외부 동작을 포트로 정의 |
| 도메인 | 서비스의 모델과 비즈니스 규칙 표현 |
| 출력 어댑터 | JPA를 통해 저장과 조회를 구현 |

프로필의 `gameId`와 `userId`는 스칼라 ID로 유지합니다. 프로필 검색의 반복 조회를 줄일 때도 연관관계 매핑을 새로 만들지 않고, 영속성 어댑터에서 필요한 ID를 모아 일괄 조회하는 방법을 택했습니다. [검색 설계 기록](https://github.com/GameMatch-Dev/Game_Match_BE/blob/main/docs/adr/GM-33-game-user-search-query-strategy.md)
