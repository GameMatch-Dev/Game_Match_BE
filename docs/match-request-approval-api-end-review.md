# 참가 신청 승인 API 종료 검토

2026-11-25. 검토 기준은 main의 `a570a6b`부터 작업 브랜치의 `036876d`까지다.
범위는 44개 파일이며 문서 커밋은 제품 검토 기준 이후에 별도로 기록한다.

## 계약과 구현 범위

사용자가 신규 계약안을 승인했다. Jira 연결 권한과 Notion 원문 조회는 사용할 수 없어
이번 검토를 Jira 원문 재확인으로 표현하지 않는다. Jira 키를 임의로 만들지 않았다.

- `PATCH /match-requests/{requestId}/status`, 본문은 `{"status":"APPROVED"}`다.
- JWT 사용자와 경기 주최 프로필의 실제 사용자 ID를 대조한다. 클럽 운영진 권한과
  거절 및 취소는 후속 기능이다.
- 신청 대표와 추가 팀원이 해당 신청의 실제 참가자다. 주최자는 주최 명단에
  명시했을 때만 인원에 포함한다. 확정된 빈 주최 명단도 허용한다.
- TEAM은 상대 신청 한 건만 승인하며 각 팀의 인원은 capacity 이하이면 된다.
  정확한 충원이나 동일 팀 인원은 요구하지 않는다. INDIVIDUAL은 주최 명단과
  기존 승인 참가자 및 신규 참가자의 전체 합계로 capacity를 검사한다.
- 권한 확인 후 동일 신청 재승인은 200이며 참가자를 중복 저장하지 않는다.
- TEAM 상대 승인 또는 개인전 정원 도달 시 `RECRUITMENT_CLOSED`로 전환한다.
- 첫 승인 이후 주최 명단 PUT은 409다. 개인전이 모집 중이어도 현재 승인 기록이
  있으면 변경할 수 없다. 권한 검사를 충돌 검사보다 먼저 수행한다.

이번 작업은 initial-code 방식이며, 사용자는 각 단계의 테스트 파일 직접 작성과
해당 RED를 해결하는 구현 묶음, 실행 및 독립 검토를 명시적으로 승인했다.
이는 이후 기능 전체에 대한 포괄적인 학습 모드 면제가 아니다.

## 저장과 응답

경기 ID만 먼저 조회하고 경기 행의 비관적 잠금을 얻은 뒤 신청을 잠금 조회 및
refresh한다. 승인 판단 정보에는 주최 명단 확정 여부와 기존 승인 참가자가 포함된다.
신청 승인, 참가자 저장과 모집 상태 변경은 Service 트랜잭션에 참여하며 승인 Adapter는
호출자 트랜잭션을 요구한다. 주최 명단 PUT도 같은 경기 잠금에 참여한다.

V7은 승인 신청 참가자 테이블을 추가한다. 주최 명단은 기존 테이블에 남겨 두고,
승인된 신청 참가자만 신규 테이블에 저장한다. 경기별 프로필 중복과 신청별 명단 순서에
UNIQUE 제약을 두며 경기, 신청, 게임 프로필에 FK를 둔다.

| 상황 | HTTP와 코드 |
| --- | --- |
| 승인 권한 없음 | 403 AUTH_403 |
| 신청 없음 | 404 MATCH_REQUEST_001 |
| 경기 없음 | 404 FRIENDLY_MATCH_001 |
| 프로필 없음 | 기존 404 GAME_USER_001 |
| 승인 정원, 명단, 상태 충돌 | 409 MATCH_REQUEST_004 |
| 모집 종료 | 기존 409 MATCH_REQUEST_003 |
| 승인 후 주최 명단 변경 | 409 FRIENDLY_MATCH_002 |
| 입력 오류 | 기존 400 COMMON_400 |

생성 응답의 기존 공개 모집 상태 코드는 0이다. 새 모집 종료 상태의 공개 숫자 코드는
임의로 추가하지 않았고 생성 응답 변환에서 해당 상태를 명시적으로 거부한다.
승인 응답은 별도 DTO를 사용하며 신청 상태 문자열과 승인된 해당 신청의 참가자를 반환한다.

## 실행 증거

전체 명령은 `.\gradlew.bat test --console=plain`이며 실제 결과는 41개 suite,
429건 통과, 실패/오류/건너뜀 0, Gradle 38초, 종료 코드 0이다.

실행은 마지막 세 테스트 커밋 직전 작업 트리에서 수행했다. 이후 소스 수정 없이
그 파일들을 커밋했고 tracked 작업 트리는 깨끗하다. 실행 당시 소스별 hash 스냅샷은
없으므로 현재 HEAD에서 재실행한 결과라고 표현하지 않는다. 별도 테스트 담당이
최신 XML, 실제 로그와 현재 테스트의 assertion을 대조했다.

- 승인 Controller 18건, 실제 JWT HTTP 통합 16건, Service 24건,
  승인 Persistence 11건을 포함한다.
- 테스트 자체의 외부 트랜잭션 없이 준비 데이터를 커밋하고 실제 Service 프록시를
  호출한다. 정상 승인 커밋이 새 트랜잭션에서도 보이는 대조 사례를 포함한다.
- 실제 Adapter 저장과 flush 후 JDBC로 참가자, 신청 승인과 모집 종료를 관찰한 뒤
  테스트 전용 장식자가 예외를 발생시킨다. 새 트랜잭션에서 세 변경의 전체 롤백을 확인했다.
- 마지막 한 자리에서 실제 JWT HTTP 승인 10건을 함께 시작해 200 한 건과 409 아홉 건,
  승인 한 건과 대기 아홉 건, 전체 실제 인원 정원 보존을 확인했다.
- 같은 신청의 HTTP 승인 10회는 모두 200이며 참가자 행은 하나다.
- 승인 SQL 반영 후 커밋을 미룬 동안 주최 명단 PUT이 H2 blocker_id에 나타나는 잠금
  대기를 관찰했다. 승인 커밋 후 PUT은 409이며 기존 명단을 유지한다.

## 독립 검토와 검증 한계

별도 Codex 리뷰어의 전체 API 검토에서 수정 필요 결함은 발견되지 않았다.
테스트 증거 점검은 별도 담당이 수행했으며 테스트를 다시 실행한 것은 아니다.
단계별 검토와 전체 종료 검토를 서로 다른 실험 결과처럼 합산하지 않는다.

런타임 증거는 H2다. MySQL 마이그레이션 파일을 작성했지만 MySQL 서버에서
실행하지 않았다. 특히 REPEATABLE READ의 초기 scalar 조회 이후 잠금 대기와
컬렉션 최신성은 MySQL에서 별도 검증할 경계다. 재현된 제품 결함이라고 단정하지 않는다.
이 테스트는 처리 성능, 낙관적 락 대비 우위나 FIFO 선착순 보장을 증명하지 않는다.

향후 승인 취소 기능이 생기면 첫 승인 이후 영구 제한과 현재 APPROVED 기록 기준의
명단 변경 제한이 같은 의미인지 정책을 재확인해야 한다. 현재는 취소 기능이 없다.

## Claude 교차 리뷰

고정 템플릿과 저장소 helper로 첫 호출을 실행했다. exit 0이었지만 findings JSON 대신
계획 파일에 결과를 쓰겠다는 문장만 반환하여 유효 리뷰로 집계하지 않았다.
동일 소스와 템플릿으로 도구를 계속 차단하고 정적 검토 system prompt와 JSON schema를
적용한 재시도에서 유효한 findings 2건을 받았다. 저장소 helper 자체는 변경하지 않았다.

| 지적 | 판정 | 근거 |
| --- | --- | --- |
| CR-1 High: 작성 모드 선택 전 무단 구현 | REJECT: 제품 무단 구현 주장 | 사용자는 initial-code를 선택했고 이후 각 RED 해결 묶음의 직접 구현을 명시적으로 승인했다. Claude 입력에 초기 모드 대기 문구를 남긴 코디네이터의 자료 준비 오류는 인정하여 정정 기록을 추가했다. 실제 승인 부재로 보지는 않는다. |
| CR-2 Medium: 기존 상대 팀 승인 분기가 도달 불가라 오류 계약 불일치 | REJECT: 계약 위반 및 미검증 주장 | TEAM 승인 후 모집 종료와 409 MATCH_REQUEST_003은 계약에 맞는다. 상대 팀 사유가 모집 종료보다 우선해야 한다는 요구는 없다. 모집 중인데 승인 기록이 있는 문맥은 Service 단위 테스트 242행에서 직접 검증하며 방어 검사로 유지한다. 모집을 열어 두라는 제안은 승인 즉시 모집 종료 계약과 충돌한다. |

CR-1의 오래된 자료 문구는 리뷰 품질 문제로 별도 기록한다. 원본 전송 자료는 보존하고
사후 정정본을 추가했으며, Claude가 정정 자료를 다시 검토했다고 주장하지 않는다.
CR-2의 정상 상태에서 검사 중복이라는 유지보수 관찰은 가능하지만, 잘못된 승인이나
계약에 없는 응답을 재현한 지적은 아니다. 다른 Codex 리뷰어에게 두 판정의 근거도 확인했다.

현재 제품 수정으로 채택한 지적은 0건이다. 수정한 제품 소스가 없으므로 추가 실행은
하지 않았고, 429건은 앞서 명시한 실제 실행 증거를 그대로 사용한다.

두 모델의 일반적 우열은 이 사례만으로 판단하지 않는다.

사용자는 이번 종료 독립 검토, Claude 외부 전송, 지적 판정과 사용량 기록 범위를
주간 잔여 7%에서 승인했다. Claude 주간 잔여는 UNAVAILABLE이다. 초기화는 사용하지 않았다.
전체 대화와 비밀 설정은 전송하지 않고 계약, diff, 선택 소스와 실제 실행 증거만 전달했다.

원격 push, PR 생성, 병합, 배포와 운영 데이터 변경은 이번 종료 리뷰에서 수행하지 않는다.
