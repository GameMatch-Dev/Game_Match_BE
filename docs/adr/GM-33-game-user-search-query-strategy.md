# GM-33 게임 프로필 검색 조회 전략

## 상태

구현됨 (2026-09-06)

- 구현 전, 서로 다른 Game/User를 가진 프로필 2개 목록 조회는 prepared statement 5회를 실행했다.
- 구현 후, 같은 목록 조회는 최대 3회를 검증하는 Hibernate Statistics 테스트가 GREEN이다.
- `GameUserPersistenceAdapterIntegrationTest` 집중 실행: 19개 테스트, 실패 0건.
- 전체 Gradle 테스트: GREEN.

## 문제

`GET /game-users/search`는 최대 20개의 게임 프로필을 페이지 단위로 반환한다.
각 항목에는 게임 정보와 사용자 ID가 필요하다.

현재 `GameUserJpaEntity`는 JPA 연관관계가 아닌 스칼라 ID를 보관한다.

```java
private Long userId;
private Long gameId;
```

변경 전 검색 어댑터는 목록의 각 행을 `GameUserProfile`로 변환할 때 다음 조회를 반복했다.

```text
GameUser 목록 조회                 1회
각 행의 Game findById              N회
각 행의 User existsById            N회
---------------------------------------
총                              1 + 2N회
```

이는 JPA Lazy Loading이 자동으로 일으키는 N+1은 아니다.
루프 안에서 Repository를 직접 호출해 생기는 **수동 N+1**이다.

Hibernate Statistics 통합 테스트에서 서로 다른 게임과 사용자를 가진 프로필 2개를 검색했을 때,
변경 전 prepared statement가 5회 실행됐고, 이것을 RED 기준으로 삼았다.

## 선택한 전략

검색 어댑터에서 **수동 배치 조회 후 Map/Set으로 재조립**한다.

```text
1. GameUser 검색 목록을 조회한다.                         1회
2. 목록의 중복 없는 gameId를 모아 Game을 IN 조회한다.     1회
3. 목록의 중복 없는 userId를 모아 User를 IN 조회한다.     1회
4. 원래 검색 목록 순서대로 GameUserProfile을 조립한다.
```

목록 조회만 보면 쿼리 수는 `1 + 2N`에서 최대 `3회`로 줄어든다.
검색 API의 `totalCount`는 별도 count 쿼리이므로 API 전체는 보통 최대 `4회`다.

### 쿼리 수 비교

현재 계약에서 `size`의 최대값은 20이다. 아래 표는 목록 조회와 `totalCount` 조회를 합친
API 전체의 최악 기준 쿼리 수다.

| 검색 결과 N | 현재 구현 | 수동 배치 | DTO Projection | CTE + Window |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 2회 | 2회 | 2회 | 1회 또는 0행 처리 필요 |
| 2 | 6회 | 4회 | 2회 | 1회 |
| 20 | 42회 | 4회 | 2회 | 1회 |

수동 배치는 최대 결과 20건에서 `42회 → 4회`로, 쿼리 수를 약 90.5% 줄인다.
DTO Projection과 CTE/Window는 더 적은 호출 수가 가능하지만, 현재 규모에서는 추가 복잡도와
이식성 비용을 함께 평가해야 한다.

## 선정 기준과 이유

### 1. 현재 모델의 경계를 유지한다

`GameUser`는 User와 Game을 소유하지 않고 `userId`, `gameId`로 참조한다.
이 구조를 유지하면 GameUser 도메인이 User/Game JPA 엔티티와 객체 그래프로 강하게 묶이지 않는다.

N+1 하나를 해결하려고 `@ManyToOne` 관계를 새로 도입하면, 엔티티 설계, Lazy Loading,
Cascade, 기존 조회 흐름까지 함께 재검토해야 한다.
수동 배치 조회는 검색 어댑터의 읽기 흐름만 바꾸므로 변경 범위가 작다.

### 2. API의 실제 상한과 맞는다

계약상 `size`의 최대값은 20이다.
따라서 한 요청에서 IN 조회 대상도 최대 20개다.

```text
gameId 최대 20개
userId 최대 20개
```

큰 IN 절에서 우려하는 파라미터 제한, 긴 SQL, 대량 객체 생성 문제는 이 API에서 사실상 발생하지 않는다.
청크 분할은 현재 요구사항에서는 과설계다.

### 3. 필요한 데이터만 명시적으로 읽는다

응답에는 Game의 `id`, `name`, `sort`, `url`이 필요하므로 Game 조회가 필요하다.
User는 `id`만 응답하지만, 현재 어댑터는 연결 User의 존재를 데이터 정합성 검증으로 사용한다.

수동 배치 조회는 다음 의도를 코드에 드러낸다.

```text
Game: 응답 조립에 필요하므로 일괄 조회
User: 연결 무결성 검증을 위해 일괄 조회
```

### 4. 동작과 쿼리 수를 예측할 수 있다

Lazy Loading이나 Hibernate Batch Fetch는 연관 객체 접근 시점과 영속성 컨텍스트 상태에 따라
실제 쿼리 수가 달라질 수 있다.

수동 배치 조회는 검색 어댑터가 항상 어떤 종류의 조회를 몇 번 실행하는지 코드와 테스트로 확인할 수 있다.

## 고려했지만 지금 선택하지 않은 대안

| 대안 | 보류 이유 |
| --- | --- |
| Fetch Join | `GameUserJpaEntity`에 `game`, `user` JPA 연관 필드가 없어 바로 적용할 수 없다. |
| EntityGraph | Fetch Join과 마찬가지로 매핑된 연관관계가 전제다. |
| Hibernate Batch Fetch | Lazy 연관관계 프록시가 없으므로 현재 구조에는 적용 지점이 없다. |
| DTO Projection | 가능하지만, 현재 스칼라 ID 구조에서는 조회 전용 쿼리 모델과 비연관 엔티티 조인/HQL 또는 Native Query 검토가 필요하다. 쿼리 1회를 더 줄일 수 있어도 현재 페이지 크기에서는 복잡도 대비 이득이 작다. |
| CTE / Window Function Projection | 1:N 컬렉션 페이지네이션, 집계, 대규모 목록 병목이 없다. DB 의존적인 Native SQL 복잡도가 현재 요구보다 크다. |
| JPA `@ManyToOne` 전면 도입 | 장래에는 가능하지만, 현재 성능 문제 하나를 위해 영속성 모델 전체를 바꾸는 것은 영향 범위가 크다. |

## 구현 시 지켜야 할 사항

1. `findAllById()`의 반환 순서에 의존하지 않는다.
   - 조회 결과는 `Map<Long, Game>`과 사용자 ID `Set<Long>`으로 만든다.
   - 최종 응답은 원래 검색 목록을 순회하며 조립해 정렬과 페이지 순서를 보존한다.
2. 연결 Game/User가 없는 경우의 기존 정합성 오류 의미를 유지한다.
   - Map/Set에서 누락을 발견하면 원래 검색 목록 순서대로 즉시 오류를 낸다.
3. Hibernate Statistics 통합 테스트에서 목록 조회 쿼리 수가 최대 3회인지 검증한다.
4. 현재 마이그레이션에는 `game_user.user_id`, `game_user.game_id`의 DB 외래 키가 없다.
   - 따라서 이번 구현에서는 Game/User 일괄 조회 후 누락을 서버 정합성 오류로 드러내는 검증을 유지한다.
   - DB 외래 키 도입은 기존 데이터 점검과 마이그레이션 영향 검토가 필요한 별도 결정이다.

## 재검토 조건

다음 상황이 확인되면 DTO Projection 또는 더 특화된 읽기 모델을 다시 검토한다.

```text
- 실제 부하 측정에서 목록 + count 4회가 병목으로 확인됨
- 응답에 User/Game의 더 많은 읽기 전용 필드가 지속적으로 추가됨
- 1:N 컬렉션을 포함한 정확한 페이지네이션이 필요해짐
- 검색 데이터 규모와 트래픽이 커져 인덱스/쿼리 계획 최적화가 필요해짐
```

## 면접·자기소개서용 요약

> 성능 개선에서 익숙한 기술을 바로 적용하기보다, 엔티티 관계 구조, API 페이지 상한,
> 변경 영향 범위, 데이터 정합성 규칙을 기준으로 대안을 비교했다. GM-33 검색 API에서는
> JPA 연관관계를 새로 도입하거나 복잡한 Native SQL을 쓰는 대신, 최대 20건이라는 계약에 맞춰
> 수동 배치 조회를 선택했다. 이를 통해 쿼리 수를 `1 + 2N`에서 최대 3회로 제한하면서
> 기존 모델과 오류 의미를 유지하도록 설계했다.
