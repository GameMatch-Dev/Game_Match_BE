# 참가 신청 API 종료 리뷰

## 범위와 계약

`POST /friendly-matches/{matchId}/requests`의 실제 JWT/Controller/Service/DB 연결을 검증한다.
대표는 본인 소유 프로필과 다른 사용자의 팀원 프로필을 지정할 수 있다.
모든 프로필은 같은 게임이어야 하고 신청자 포함 중복 ID는 거부한다.
팀원 목록 생략/null은 빈 목록으로 처리한다. 대기 신청은 정원을 차감하지 않는다.
신규는 201, 취소/거절된 신청의 재신청은 같은 ID와 새 명단/메시지로 갱신해 200이다.
활성 신청 중복은 409이며 공개 성공 데이터는 requestId다.

사용자가 계층별 테스트와 그 RED를 해결하는 파일 묶음의 AI 작성을 승인했다.
이번 검증과 리뷰 수정도 해당 참가 신청 API 범위에 한정한다.

## 실행 증거

- 최초 제품 코드 전체 테스트: 244개 통과.
- 새 JWT HTTP 통합 테스트: 17개 통과, Gradle 23초, exit0.
  SpringBootTest와 실제 보안/서비스/저장을 사용한다. 테스트 트랜잭션의 flush/clear로
  DB 결과를 확인하며 독립 HTTP 요청의 커밋 완료를 별도로 증명하는 테스트는 아니다.
- 재신청 경합 수정 전: 독립 H2 트랜잭션 둘이 같은 CANCELLED 상태를 읽도록 제어했다.
  성공 1건을 기대했지만 2건 모두 성공하여 테스트 1개 실패, exit1, 약19.94초.
- 조건부 상태 변경 및 refresh 수정 후: HTTP17 + 경합1 + Persistence17 = 35개 통과,
  exit0, 약57.70초. 원래 ID와 승자 메시지가 저장됨을 확인한다.
- 프로필 일괄 조회 테스트를 먼저 추가했을 때는 메서드 부재로 compileTestJava 오류8개,
  exit1. 테스트 본문은 실행되지 않았다.
- 일괄 조회 구현 후 대상 테스트: 프로필 Service5 + 프로필 Persistence24 + 신청 Service16 +
  신청 HTTP17 = 62개 통과, exit0, 약32.23초. 서로 다른 게임/사용자 3개를 가진 프로필을
  캐시 없이 읽는 회귀 테스트에서 최대3쿼리, 빈 입력은0쿼리를 확인했다.
  이는 임의 크기의 요청이나 모든 DB 드라이버의 바인드 제한을 검증했다는 뜻이 아니다.
- 최종 `.\gradlew.bat test`: exit0, Gradle39초(도구39.535초),
  267개, 실패0/오류0/생략0. 새 신청 HTTP17개와 경합1개, 기존 생성 API 통합6개를 포함한다.

## Codex 독립 리뷰

재신청 경합 1건을 지적했고 ACCEPT했다. 읽기 시점의 비활성 상태만 확인한 뒤 같은 ID를
UPDATE하므로 신규 행의 UNIQUE 제약으로는 경합을 막을 수 없었다.
신청 행이 여전히 CANCELLED/REJECTED일 때만 PENDING으로 바꾸는 조건부 UPDATE를 적용했다.
갱신 0건은 중복 신청 예외로 거절한다. 기존 영속성 문맥은 refresh 후 명단을 반영한다.
조건부 갱신과 명단 저장은 한 트랜잭션이며 수정 후 독립 재검토에서 잔여 지적은 없었다.
팀원 일괄 조회 수정과 새 테스트도 구현 담당과 다른 Codex가 재검토했고 추가 지적이 없었다.

## Claude 교차 리뷰와 판정

사용자가 이번 API의 명세, 변경 코드, 관련 소스와 테스트 결과를 Anthropic으로 전송하는
범위를 명시적으로 승인했다. 고정 리뷰 템플릿에 해당 자료만 넣고 도구 없는 읽기 전용
호출을 수행했다. 이전 CLI 진단에서 확인한 명시적 reviewer system prompt, dontAsk,
빈 tools, safe-mode, no-session-persistence, findings JSON schema 조합을 재사용했다.
이 호출은 재신청 수정 전 코드 기준이며 수정 뒤 새 Claude 리뷰를 실행한 것으로 세지 않는다.

## 남은 범위와 한계

- 테스트 DB는 H2다. MySQL 런타임/격리 수준/부하 성능을 검증한 것이 아니다.
- 현재 경기 enum은 RECRUITING만 있으므로 비모집 상태의 실제 저장 전이를 추가하지 않았다.
- 경합 회귀 테스트는 같은 취소 신청의 빈 팀 명단 사례다. 모든 승인/취소 경합의 증거가 아니다.
- 승인·취소·참가자 정원 처리는 후속 API다. 이번 조건부 신청 갱신은 그 비관적 락 설계를 대체하지 않는다.
- Jira는 마지막 확인에서 tenant suspended-inactivity라 작업 키를 확인하지 못했다.
  번호를 임의로 만들거나 기존 GM-35에 연결하지 않았다. 로컬 작업 브랜치를 사용한다.
- 원격 PR/CI, main 병합, 배포 및 브랜치 삭제는 이 문서 작성만으로 수행되지 않는다.
