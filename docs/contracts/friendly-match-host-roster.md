# TEAM 친선경기 호스트 팀 명단 계약

2026-11-24 사용자 정정과 승인 정책을 기록한다. 이 문서는 승인된 정책과
아직 승인되지 않은 API 제안을 구분하며, 제안만으로 구현을 승인하지 않는다.

## 승인된 정책 (APPROVED)

- TEAM은 호스트 한 팀과 상대 한 팀으로 구성된다.
- `capacity`는 대표자를 포함한 **각 팀의 최대 인원**이다. 5대5의 값은 5이며
  10이 아니다. 호스트는 호스트 팀 인원에, 상대 대표자는 상대 팀 인원에 포함된다.
  정확히 capacity명으로 채우거나 양 팀 인원이 같아야 하는지는 아직 확정하지 않았다.
- 경기 생성 시 호스트 팀 명단을 몰라도 된다. 명단 미확정 상태에서도 상대 팀의
  참가 신청을 받을 수 있다. 단, 상대 팀 참가 신청을 승인하기 전에는 호스트 팀
  명단을 확정해야 한다.

이 capacity 정정은 TEAM에 한정하며 INDIVIDUAL의 의미를 새로 정의하지 않는다.
2026-11-24 사용자 설명이 과거의 전체 참가 정원 해석보다 우선한다.

## API 제안 — 승인 대기 (PROPOSED)

아래 필드명, 상태 표현, 요청/응답 형태 및 검증 규칙은 제안이며 확정 계약이 아니다.

### 생성 요청 확장 제안

- 선택 필드 `hostTeamMemberIds`를 추가한다. 목록에서는 호스트의 게임 프로필을
  제외하고, 호스트는 자기 팀 인원에 자동 포함하는 방안을 제안한다.
- 필드 생략 또는 `null`은 `UNCONFIRMED`로 표현한다.
- 목록이 제공되면 검증을 통과한 명단을 `CONFIRMED`로 표현한다.
- 빈 목록 `[]`은 호스트만 있는 팀으로 해석하고 `capacity >= 1` 범위에서 허용하는
  방안을 제안한다. 이 빈 목록의 확정 처리와 구체적인 목록 검증은 사용자 승인 대기다.

### 명단 교체 API 제안

- `PUT /friendly-matches/{matchId}/host-roster`로 명단 전체를 교체한다.
- JWT 인증 사용자와 실제 경기 호스트를 확인하는 권한 검사를 제안한다.
- 요청 본문의 `teamMemberIds`는 필수로 하고, 호스트 프로필은 목록에서 제외하는
  방안을 제안한다.
- 성공 응답은 `200`으로 하고 확정 상태, 인원수, 프로필 ID 목록 등을 반환하는
  방안을 제안한다. 정확한 응답 필드와 형태는 아직 정하지 않았다.

프로젝트 탐색에서 기존 호스트 명단 PUT 계약을 찾지 못했다. 따라서 위 경로는
기존 계약으로 취급하지 않는 **신규 제안**이다.

## 미결정 사항 (OPEN)

- 위 생성 필드와 PUT 경로, 요청/응답 형태 및 명단 확정 표현의 승인 여부.
- 상대 팀 참가 승인 후 호스트 명단 변경 허용 여부와 처리 방식.
- 양 팀에 동일한 사람이 포함되는 경우의 허용 여부와 검증 방식.
- 호스트 팀 최대 인원 검사를 수행할 시점, 오류 응답 및 구체적인 검증 계약.
  승인된 팀별 최대 인원 의미와 별개로 이 API의 세부 검증은 아직 승인되지 않았다.
- 명단 확정·교체와 상대 팀 참가 승인이 동시에 발생할 때의 처리 정책.

미결정 사항을 추정하여 구현하지 않는다. 정확히 capacity명 또는 동일 인원의
완성된 N:N 팀을 요구하는 최소 인원·충원 조건을 추가하지 않는다.

## 기존 자료와 구현 범위

- 과거 생성 계약: [Notion 생성 문서](https://www.notion.so/91ab13d8d44182c8aa2301900b493d5a).
- 과거 참가 승인 계약: [Notion 승인 문서](https://www.notion.so/5aab13d8d44183009a4f812f8a60f4d5).
- 입력 검증 기록: [GM-35 ADR](../adr/GM-35-create-input-validation.md).

과거 계약과 ADR은 당시 기록으로 보존하되, TEAM capacity의 전체 정원 해석은
2026-11-24 정정으로 대체한다. 위 과거 문서 링크는 참고 자료이며 신규 PUT 계약의
존재나 승인 근거가 아니다.

현재 코드는 양수 capacity를 저장하며, 이 정정을 위해 값을 2로 나누거나 새 참가
승인 인원 산식을 추가할 근거는 없다. 후속 작업은 계약 문서와 승인된 정책을
검증할 테스트에 정정을 반영해야 한다. 이 의미 정정 자체는 DB 숫자 마이그레이션이나
스키마 변경을 요구하지 않는다. 이 문서 작업에서는 백엔드 코드를 변경하지 않는다.
