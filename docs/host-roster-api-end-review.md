### ACCEPT: 연결 사용자 정합성 검사 차이

새 [FriendlyMatchPersistenceAdapter](../src/main/java/com/hd/gamematch/friendlymatch/adapter/out/persistence/FriendlyMatchPersistenceAdapter.java)는
프로필과 게임을 직접 읽어 host를 생성하지만 `users` 행의 존재를 확인하지 않는다.
기존 [GameUserPersistenceAdapter](../src/main/java/com/hd/gamematch/gameuser/adapter/out/persistence/GameUserPersistenceAdapter.java)의
단건/일괄 복원은 연결 사용자 미존재를 정합성 오류로 처리한다. 기존 테스트에도 이 정책이 있다.
V1 스키마에는 `game_user.user_id`의 사용자 외래 키가 없다.

따라서 프로필과 게임은 남아 있으나 연결 사용자가 없는 상태에서 해당 subject의 유효 JWT가
존재하면 새 PUT 경로는 그 host를 복원해 `[]` 명단을 저장할 수 있는 검사 차이가 있다.
현재 앱의 사용자 삭제 경로는 확인되지 않았으므로 정상 요청에서 일반적으로 발생하는
중간 심각도 보안 결함으로 과장하지 않고 P3 조건부 정합성 보완으로 판단한다.
이번 판정은 코드/스키마/기존 정합성 테스트 대조이며 새 실행 재현은 수행하지 않았다.

이 항목은 최초 Codex 전체 보고에는 없고 Claude가 먼저 지적한 독립 발견이다.
후속은 고아 host-user 조건의 RED 테스트를 만들고 검사 일관성을 맞추는 작업이다.
Claude가 제안한 입력 UseCase 주입 방식 자체를 필수 해법으로 채택한 것은 아니다.

### REJECT: 검증 중복의 결함 분류

[CreateFriendlyMatchService](../src/main/java/com/hd/gamematch/friendlymatch/application/service/CreateFriendlyMatchService.java)의
validateRoster와 [ConfirmHostRosterService](../src/main/java/com/hd/gamematch/friendlymatch/application/service/ConfirmHostRosterService.java)의
검증이 같은 것은 사실이다. 향후 정책 변경 시 함께 수정해야 한다는 위험은 기존 Codex
단계 검토와 계약 기록에 이미 남겼다. 현재 구현의 오동작을 뒷받침하는 증거가 없으므로
이번 종료 리뷰의 필수 결함으로 채택하지 않는다. 공통화의 장단점은 별도 구현 범위에서 판단한다.

## 계약과 범위

- 생성의 선택 명단과 명단 확정 PUT, 권한과 오류 처리, 순서 저장/교체, CORS와 V6 스키마를 검토한다.
- 주최 권한과 실제 참가는 별개다. 주최자는 명시한 경우에만 참가자다.
- 명시적 `[]`은 0명 확정, 생성의 생략/null은 미확정, PUT의 생략/null은 400이다.
- TEAM의 capacity는 팀당 최대 인원, INDIVIDUAL은 경기 전체 최대 인원이다.
- 중복/게임 불일치/정원 초과 400, 미존재 프로필 404. 권한 확인 후 일괄 조회하며 저장 전에 검증한다.
- 후속 상대 승인 기능의 승인 후 변경, 양측 중복 참가, 승인/명단 교체 경합은 이번 구현 범위가 아니다.

요구사항은 [사용자 승인 계약](contracts/friendly-match-host-roster.md)을 따른다.
Jira 재연결에서 이전 GameMatch tenant는 허용되지 않았고 현재 허용된 tenant의
`project = GM` 조회는 빈 결과였다. 원격 요구사항을 재검증하지 못한 한계이며,
과거 이슈가 없었다는 증거나 새 Jira 키를 임의로 만들 근거가 아니다.

## 실행 증거

- 기존 전체 실행: `.\gradlew.bat test`, exit 0, Gradle 44초.
- 실제 XML: 35개 suite, 344건, 실패/오류/건너뜀 0.
- 실제 JWT 생성 16건과 명단 PUT 15건 및 별도 생성 롤백 1건이 전체 실행에 포함된다.
- 현재 소스/테스트는 해당 실행과 일치한다. 이번 검토에서는 재실행하지 않고 원본 로그와 XML을 점검했다.
- 보통 HTTP 통합 테스트의 테스트 트랜잭션과, 별도 비트랜잭션 테스트에서 증명한 생성 실패 롤백을 구분했다.

## 독립 검토 내용과 한계

Codex는 전체 제품 변경과 관련 테스트, MySQL/H2 V6 마이그레이션을 대조했다.
인증 사용자/주최자 대조, 참가자 조회 전 권한 검사, 생성 저장 전 검증, 명단의 정확한 전달,
확정 상태와 순서/교체/경기별 분리 및 트랜잭션 참여에서 최초에는 수정 필요 결함을 보고하지 않았다.
이후 Claude의 사용자 존재 확인 누락을 별도 재검토하여 위 조건부 P3를 인정했다.

실제 런타임 증거는 H2다. MySQL 실행/동시성/성능이나 운영 마이그레이션을 검증했다는 뜻은 아니다.
일반적인 성공 HTTP 요청의 독립 커밋 경계와 동시 PUT 직렬화를 증명하는 테스트는 없다.
이 한계를 증명된 제품 결함이나 후속 승인 기능의 완료로 바꾸어 기록하지 않는다.

## 승인과 사용량

기존 helper의 plan 모드로 실행한 첫 호출은 exit 0이지만 `findings` JSON 대신
계획 파일에 결과를 쓰겠다는 문장만 반환했다. 결과 형식 검증에 실패했으므로 완료 리뷰로
집계하지 않는다. 동일 고정 템플릿과 소스 묶음으로 재시도하되 도구/파일 접근은 계속
차단하고 정적 리뷰 system prompt와 JSON schema를 사용했다. 첫 호출도 비용과 시간에 포함한다.

첫 호출 CLI 보고: 199.435초, $0.5636086. 입력 2, cache 생성 79,139, cache 읽기 3,293,
출력 18,754(thinking 18,689) tokens. CLI 비용에는 보조 모델 사용이 포함된다.

실제 호출 wrapper 벽시계 합계는 393.901초다. 비용은 CLI 보고값이며 별도 청구 내역을 조회한
것이 아니다. 결과 형식 실패도 제외하지 않고 계산했다. 소스 변경 후 재리뷰는 하지 않았다.
기존 helper의 출력 검증/계획 모드 문제는 별도 도구 개선 후보이며 이번 리뷰에서 helper를 수정하지 않았다.

사용자는 현재 종료 리뷰의 Codex 독립 검토/테스트 증거 점검과 준비한 약 179KB의
요구사항/변경 코드/선택 소스/실행 증거를 Anthropic Claude로 전송하는 것을 승인했다.
주간 잔여 50% 미만 호출 예외도 이번 종료 리뷰 범위로 승인했다.
대화 전체와 비밀 설정은 전송 자료에서 제외했으며 초기화 크레딧을 사용하지 않았다.

- 실제 실행 시작: 주간 42%, 5시간 79%.
- Claude 호출 직전: Codex 주간 40%, 5시간 68%; Claude 주간 잔여는 `UNAVAILABLE`.

원본 리뷰/실행 산출물은 작업의 로컬 `host-roster-end-review` 폴더에 보관하며 원본 소스 묶음은
